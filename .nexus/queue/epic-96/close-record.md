# Close Record: Deploy Raiden to AWS from the terminal

## Key Decisions

- **D1 — Define the infrastructure with AWS CDK in TypeScript, as a new Nx project (#106).** All Raiden AWS resources are written as AWS CDK code in TypeScript, in a new Nx project beside the backend. CloudFormation in the team's account holds the deployment's state. The setup command runs the bootstrap when the account has none, and uses the default bootstrap, as the lead chose. **Why:** The state lives in the account, so a second lead, or the same lead on a fresh checkout, can update the deployment with only credentials, which the epic's first success metric needs. It is TypeScript, which matches the TypeScript-only standard, and it installs through pnpm, so a lead needs no new tool binary beyond Node and Go. Its assertion tests run in the existing vitest setup without credentials. Its deploys roll back automatically, which #99 needs. **Refuted alternative:** Terraform or OpenTofu, which uploads the backend zip directly and needs no bootstrap resources. It lost on state. A local state file is lost with the machine and cannot be committed. A shared remote state needs a state bucket created by hand before the first run, so the deployment would still have resources outside the repository.
- **D2 — Two stacks: one for the backend, one for web hosting (#106).** The backend stack holds the table, the function, its function URL, its role and both settings stores. The web hosting stack holds the bucket and the distribution. Neither stack takes a value from the other: the backend address reaches the web view through the build, and the allowed origins come from the settings. Setup deploys both stacks, the backend update deploys only the backend stack, and the web view update deploys only the web hosting stack. **Why:** #101 requires that a web view update leaves the backend unchanged, and with separate stacks the web view update never touches the backend stack. #99 updates only the backend, so it never touches the hosting. Stacks with no shared values avoid locked cross-stack exports. **Refuted alternative:** One stack for everything, which is simpler, with one deploy and one output list. It lost because every web view update would also deploy the backend function. That breaks #101 acceptance criterion 3 whenever backend changes are waiting, and it would make a web view update need a Go build.
- **D3 — The distribution serves only the web view, and the backend keeps its own address (#106).** The CloudFront distribution routes only the static files. The web view keeps calling the backend at the function URL, cross-origin. The single origin raised by #34 D4 is not built. **Why:** A single origin removes no cross-origin work, because the extension calls the backend from its own origin in every case, so the origin check and the allowed-origin list stay. Locking the function behind CloudFront with origin access control needs the browser to send a hash of each POST body, which would be a web view code change, and the epic rules that out. Without that lock the function stays public, and the extra CloudFront path adds a hop and restricts nothing. The backend routes on exact paths, so an API under a sub-path would need a rewrite at the edge or a backend change. The gain would be one skipped preflight on sign-in and on token renewal, which are rare calls. The choice can be reversed later, because the backend address is a build setting. **Refuted alternative:** Route the API through the same distribution under a sub-path. It gives the one origin #34 D4 hoped for, and it lets the content policy name only the page's own address. It lost because it costs an edge rewrite and a no-cache path that forwards the Origin header, and it does not work with origin access control for POST, all to avoid one preflight.
- **D4 — Expose the backend through a Lambda function URL, with the backend's own origin check as the only cross-origin policy (#106).** The backend address is a public function URL with the function URL's own cross-origin feature left off. The function is built for arm64, which matches the existing build. The function has a fixed name, so a change that would replace it fails instead of silently changing the address. **Why:** The handler already takes the payload format that function URLs send. It routes by method and exact path, and it answers preflights and origin checks itself. A function URL costs nothing extra. Turning on the function URL's own cross-origin feature would add a second policy that could disagree with the handler's allowed origins. **Refuted alternative:** API Gateway HTTP API, which gives built-in throttling, access logs and an easier path to a custom domain. It lost because custom domains are out of scope, one team's sign-in calls need no throttling, and it adds a resource and a cost per request that these stories do not use.
- **D5 — One retained table with the local shape and deletion protection on (#106).** The backend stack creates one on-demand table with the same key shape as the local table and a fixed name. The table is kept if its stack is deleted, and its deletion protection is on. The function's environment names the table. The function's role may use only this table, its two settings stores and its logs. **Why:** #99 needs stored data to survive updates. With a fixed name, a change that would replace the table fails instead of creating an empty one. Deletion protection and retention keep the data even through a mistaken stack change. The epic assumes one deployment per account, which makes a fixed name safe. **Refuted alternative:** none
- **D6 — Settings live in two Secrets Manager entries that the infrastructure creates empty, and the backend reads them at start (#106).** The client secret goes in the client secret store. The client ID, the allowed return addresses and the allowed origins go in the sign-in settings store. The infrastructure creates both entries with no value and never writes one. The settings command writes them from the terminal and reads the secret only from a hidden prompt or from standard input. When it starts, the backend reads both entries in place of the four environment values, and local runs keep the environment. This is a backend code change; the epic rules out only web view code changes. **Why:** #98 asks that the secret appear in no repository file and no build output. A secret passed through the infrastructure would sit in the generated templates, and a secret passed as an environment value would show in the function's configuration. Entries created with no value mean a later stack change can never reset a value the lead wrote, and every resource is still defined in the repository. The second entry lets the web view update read the client ID without fetching the client secret, so the web build cannot leak the secret, and the web view's client ID always matches the backend's. A mismatch causes the documented "incorrect client credentials" failure. This follows the standard that secrets load from the environment or from AWS secrets. **Refuted alternative:** An SSM Parameter Store SecureString for the secret, which costs nothing, with plain parameters for the rest. It lost because CloudFormation cannot create SecureString values, so the settings command would create the parameter outside the repository's infrastructure. Plain parameters also need a value in the template, and a later template change would write that placeholder back over the lead's setting.
- **D7 — A settings change takes effect by recycling the function, not by a timed re-read (#106).** After it writes the stores, the settings command recycles the function by setting a settings-version value that holds no secret. The command waits until the update finishes and checks health. If a store is empty, sign-in stays off. If a store cannot be read, the instance fails to start. **Why:** #98 needs the new value used without a code build, and a lead testing right after a change needs it to take effect at once. Reading once at start keeps the backend code simple. Failing to start on a read error shows the fault in health instead of silently turning sign-in off. **Refuted alternative:** Re-read the stores when the cached values are older than a few minutes, which keeps the infrastructure the only writer of the function's configuration. It lost because a lead who fixes a return address waits up to that interval with confusing failures, and it adds cache and refresh-failure code to the backend.
- **D8 — Backend updates: a repeatable build first, a stack deploy that rolls back, then a health check (#106).** The backend update builds before any upload, and the backend build is made repeatable, so its output does not depend on the checkout path, the version-control state or the zip's timestamps. The stack deploy always keeps CloudFormation's rollback on and never uses AWS CDK's direct "hotswap" path. The command finishes with a health check and fails when the answer is not ok. Code that deploys but fails the health check is recovered by hand, by redeploying the previous commit, as the lead chose. **Why:** #99 acceptance criterion 3 means a failed build or upload must change nothing, and a failed stack update must return to the old code, which CloudFormation rollback gives. A repeatable binary means an unchanged checkout uploads no new code, which the epic's repeat-run success metric needs. Today's build stamps the checkout path and the zip time, so every run would look changed. **Refuted alternative:** Publish a version for each deploy, point the function URL at an alias, and move the alias only after a health check passes. This also falls back when new code deploys but crashes at start. It lost because the story asks only about failed builds and uploads, and it adds versions, an alias and a gated switch to an S-sized story.
- **D9 — The deploy gives the web view build its three settings from the deployment itself (#106).** The web view update reads the backend address and the web view address from the stack outputs, and the client ID from the sign-in settings store. It passes exactly these three values to the existing web view build, ahead of any local settings file. The existing build already writes the backend origin into the page's content policy. The build refuses to run when the client ID is not set. **Why:** #100 says the web view is built against the deployed backend address. Reading the values from the deployment removes typing mistakes, and it makes the web view's return address match the address the settings allow. Refusing to build without a client ID avoids uploading a web view whose sign-in cannot work. This needs no change to the web view's code. **Refuted alternative:** Have the lead put the three values in the local frontend settings file, as for a local build. It lost because it brings back client-ID and return-address mismatches, and a fresh checkout would not have the file.
- **D10 — The deploy command uploads the files itself: changed files only, page last, then a waited invalidation (#106).** The upload is part of the web view update command, not a resource inside the stack. It compares each file's content with the bucket and uploads only the changed files, each with its correct content type and a revalidate header. It uploads the page last and deletes removed files after the page. It sends one invalidation for every path only when a file changed, and it waits for the invalidation to complete before it reports success. **Why:** #101 needs the web view address to serve the new files when the command ends, with no manual cache clear. Uploading only changed files keeps a repeated setup from changing anything, because the build system's cache gives back the same files when nothing changed. Uploading the page last makes it unlikely that a page from one build loads the script of another. A single every-path invalidation counts as one path in the free monthly allowance. **Refuted alternative:** AWS CDK's own bucket-deployment construct, which keeps the upload inside the stack and can invalidate too. It lost because it installs a helper function and a layer in the account, it needs a separate deployment for each set of headers, its failures show up as slow stack rollbacks, and it would re-upload on every build because the service worker file always changes.
- **D11 — The browser revalidates every file, and the edge keeps files until the next deploy (#106).** Every hosted file tells the browser to revalidate on each load: the page, the script, the service worker, the manifest, the font and the icons. The edge may keep files until the deploy's invalidation. The file names carry no content hash, so no file is marked as long-lived. **Why:** #101 acceptance criterion 2 forbids a stale service worker or manifest. The web view's file names are fixed, and changing them to hashed names would be a web view code change, which is out of scope. Revalidation costs one small conditional request for each of about eight files, answered "unchanged" by the edge. It keeps the recorded web view behaviour that a connected load never runs an old build. **Refuted alternative:** Long cache lifetimes with content-hashed names, which is faster on repeat loads. It lost because it needs build and code changes the epic rules out.
- **D12 — A private bucket reached only through the distribution, on CloudFront's own HTTPS address, with no request logging (#106).** The bucket blocks all public access and allows reads only from this distribution, through origin access control. The distribution redirects plain HTTP to HTTPS on its default address and serves the page for the root address. Request logging is off. The font and icons are already part of the web view build, so they come from the same address with no extra work. **Why:** #34 D4 decided this hosting, and it meets #100 acceptance criterion 2. Custom domains are out of scope, so the default address gives HTTPS with no certificate. With logging off, the sign-in return address, which carries a one-time code in its query, is written to no log, in keeping with the github-sign-in page's invariant 3. **Refuted alternative:** none
- **D13 — Four commands: root scripts that run Nx targets which are never cached (#106).** There are four commands: setup, settings, backend update and web view update. Each is a root package script that runs a target on the new infrastructure project. The targets depend on the build targets, so a failed build stops the deploy. The targets are never cached, and none is named deploy, because pnpm has a built-in command of that name. Setup is the same idempotent path as the two updates, run together, with no separate creation logic. The project's build, test and type-check targets need no AWS credentials and never call AWS. The deploy logic uses the AWS SDK, not the AWS command-line tool, so a lead needs Node, pnpm, Go and credentials. **Why:** The epic asks for one command per update and an idempotent setup, and CloudFormation deploys are idempotent, so one path serves both. The Nx targets reuse the repository's existing build dependencies and caches. Keeping AWS out of the build, test and type-check targets keeps them working on any machine and in CI. **Refuted alternative:** Shell scripts beside the existing emulator script, which are quicker to write. They lost because they do not reuse the Nx build graph, and they would need the AWS command-line tool plus separate argument parsing and tests.
- **D14 — The guide gives the first-run order and the permissions for each phase (#106).** The deployment guide gives the first-run order: setup, register the callback, settings, web view update. It covers both updates and settings changes. It names the permissions by phase: the one-time bootstrap, routine deploys through AWS CDK's roles, and the direct calls the commands make to the stores, the function configuration, the bucket and the distribution. It names the bootstrap resources and what they grant. It is linked from the GitHub App setup page, whose section on giving the backend its settings points to the settings command. **Why:** #102 asks for a guide a lead can follow from a fresh checkout, with the permissions their credentials need. Splitting the permissions by phase lets a team keep the broad bootstrap rights out of everyday credentials. **Refuted alternative:** none
- **The root scripts are aws:setup, aws:settings, aws:update-backend and aws:update-web.** (a decision stub the verdict on sameera/raiden#109 confirmed). **Why:** pnpm has built-in setup and deploy commands, so plain names would run pnpm's own command. **Refuted alternative:** Plain setup, which pnpm setup shadows.
- **The backend stack creates the function's log group and a role whose only statements name the table, the two stores and that log group.** (a decision stub the verdict on sameera/raiden#109 confirmed). **Why:** The default Lambda role attaches AWSLambdaBasicExecutionRole, which allows logs on every resource, and G12 limits the role to its own logs. **Refuted alternative:** The default role from AWS CDK, plus table grants.
- **The distribution uses a cache policy whose minimum TTL is one year, and the files carry Cache-Control: no-cache.** (a decision stub the verdict on sameera/raiden#109 confirmed). **Why:** CloudFront caches a no-cache response for the minimum TTL and passes the header to the browser, so the edge keeps files until the invalidation and the browser still revalidates (D11). **Refuted alternative:** The managed CachingOptimized policy, whose one-second minimum TTL sends almost every request to the bucket.
- **pnpm aws:settings refuses every argument and asks for each value; piped standard input answers the prompts line by line.** (a decision stub the verdict on sameera/raiden#109 confirmed). **Why:** With no arguments the client secret can never reach shell history or the process list (G8). **Refuted alternative:** Flags for the client ID and addresses with only the secret prompted.
- **infra/src/app.ts skips the backend stack when .tmp/lambda.zip is missing and the deploy targets the web stack.** (a decision stub the verdict on sameera/raiden#109 confirmed). **Why:** The web view update deploys only the web stack and must not need a Go build (D2), but CDK synthesizes every stack in the app. **Refuted alternative:** Two separate CDK apps.
- **The upload finds changed files by comparing each stored object's ETag with the local file's MD5.** (a decision stub the verdict on sameera/raiden#109 confirmed). **Why:** A single-part upload with S3-managed encryption has its MD5 as its ETag, so no extra metadata or state file is needed. **Refuted alternative:** Storing a hash in object metadata, which needs one HEAD request per file.
- **When no file changed, the web view update still invalidates if the newest stored object is newer than the newest completed invalidation.** (a decision stub the verdict on sameera/raiden#109 confirmed). **Why:** Only a time comparison lets a retry clear the cache after a failed invalidation while an unchanged deployment still clears none (G2, G23). **Refuted alternative:** A local marker file recording a pending invalidation.
