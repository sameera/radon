# Close Record: Grooming shows the backlog in sprint bands under milestone headers

## Key Decisions

- **D1 — The backend runs the sync as the signed-in lead (#93).** The Grooming sync runs in the backend. The browser sends the lead's token on each backend data request, through the same client that sends GitHub requests, with the same renewal and failure kinds. The backend reads GitHub with that token, and that read is also its check that the caller may see the repository. The backend stores nothing of the token. **Why:** The initiative settled that Raiden keeps milestones and sprints in its own database, synced from GitHub. Those records are shared by the whole team, so the backend must read them from GitHub itself; data a browser posts could be forged. The later epics write goals, assignments and Raiden-made sprints, and a trusted write needs a caller GitHub has confirmed for that repository. GitHub, called with the caller's token, is the only way Raiden can confirm who is calling. The backend already receives the refresh token, which can mint new access tokens, so it is already trusted with the lead's GitHub access. The token is read-only. **Refuted alternative:** The browser reads milestones and iterations through the gateway and posts them to the backend. It keeps the github-client page's token rule word for word and puts no GitHub calls in the backend. It lost because the backend cannot tell real GitHub data from forged data, so any browser could overwrite the team's shared records, and #82 would have to send the token to the backend anyway to authenticate its writes.
- **D2 — One partition per repository, keyed by the repository's permanent identity (#93).** The existing single table holds one partition per repository, keyed by GitHub's permanent identity for the repository, which the backend reads on each sync. Milestones and sprints are separate records, each with the origin marker. Later goals and assignments are their own records in the same partition, keyed by sprint identity and issue identity, never fields on a sprint record. A sync writes and deletes only records marked as synced. **Why:** The permanent identity survives a rename or a transfer, so the records the lead owns are never left behind. The backend learns it from the read it already makes. Separate records mean a sync cannot overwrite a goal or an assignment, and one query serves the whole page. **Refuted alternative:** Owner and name as the key, with goals as fields on the sprint record. The key is readable and needs no lookup, and the page reads fewer records. It lost because a rename or transfer would leave every Raiden-owned record behind, and a goal field would be deleted with its sprint record.
- **D3 — The sync source is picked once and kept (#93).** When no source is recorded, the backend picks the earliest-created linked project the caller can read that has an iteration field, and within it the earliest-created iteration field. The pick is recorded and kept. A caller who cannot read the recorded project changes nothing and sees a named cause. The pick is cleared, its synced sprints deleted and a new pick made only when a caller who can read the project finds it unlinked or without the field. **Why:** The goals and assignments of #82 and #83 key on sprint identity, so a source that changes between loads, or between leads who see different projects, would swap every sprint and leave those records behind. Project numbers repeat between an organization and a user, and GitHub's list order can change when a project is linked. A lead who cannot see a project must not be able to delete everyone's sprints. **Refuted alternative:** Work out the first linked project with iterations on every load, as the epic's assumption reads. It needs no stored state. It lost because the answer depends on who is looking and on linking order, and each change leaves sprint-keyed records behind.
- **D4 — What a sync covers, and what removal does (#93).** Sprints are every iteration on the source field, active and completed, with name, start date and end date. Milestones are every milestone, open and closed, with title, due date, description and state. A renamed or re-dated item updates in place. An item GitHub no longer has is deleted. Records keyed to a sprint are never deleted or changed by a sync. **Why:** Past sprints live in GitHub's completed list and need bands. Closed milestones still head past sprints. Keeping sprint-keyed records means an edit in GitHub cannot destroy the lead's own text. **Refuted alternative:** Mark a removed item as removed and hide it, instead of deleting it. A later goal would keep its sprint's name and dates. It lost because Raiden's synced records would no longer match GitHub, which stories #85 and #86 require.
- **D5 — Bands only after a complete load (#93).** Bands show only when both the sync and the backlog load succeeded. Either failure shows its named cause and one Try again that reruns both. The causes are: signed out, cannot read the repository, rate limit, cannot read the project that supplies sprints, Raiden's backend unavailable, and other. Stored records are not shown when the sync fails. **Why:** It follows the live-backlog page's rule to show only complete loads. Showing stored records without a sync would need a second way to check access, and would break "a change shows on the next page load". **Refuted alternative:** On a sync failure, show the backlog in one band with a warning, so the lead can still browse issues. It lost because the band's "no sprint" label would be false for issues that have a sprint.
- **D6 — The browser reads each issue's sprint during the backlog load (#93).** The backlog load also reads each issue's iteration values on its project items, through the gateway. The browser matches them to sprints by the sync source's field and iteration identity. A read GitHub reports as incomplete is completed or fails the load. No assignment is stored in this epic. **Why:** It keeps the live-backlog page's invariants 5 and 6: the backlog reads GitHub only through the gateway, and titles never reach the backend. The values come in the same answers the backlog already reads. **Refuted alternative:** The backend reads every issue's iteration during the sync and returns which sprint each issue is in. The browser would do less work. It lost because the backend would page through every project item on each load, repeating the browser's search, and issue data would start reaching the backend.
- **D7 — Band rows keep today's list form (#93).** In each band, rows form today's tree, limited to the band's issues. A parent in the same band is a row. A parent in another band, or one the query did not return, shows only as a crumb above its group, and a parent outside the query still says so and gives its state. Order, collapse and filter work as today, inside each band. **Why:** It reuses the tree and crumb form the mockup keeps, and puts each issue in exactly one band. **Refuted alternative:** none
- **D8 — The band view replaces both panels for the signed-in lead (#93).** With a live GitHub connection, Grooming shows only the band view. It has two columns. The goal column holds the milestone headers and the sprint cards. The backlog column holds only issue rows and crumbs. D15 sets which column is on which side, and D17 sets what a card holds. The sample goals panel, its ranking, Undo and Save plan do not show in the band view. A host with no live connection keeps today's sample page until #82 removes it. The divider, the preferred width and keyboard resizing carry over to the columns, as D16 and D18 describe. **Why:** Story #88 requires two columns. Sample goals beside real sprints would read as real data. Removing the sample code is #82's work, and the sample page still covers the plan rules in tests. **Refuted alternative:** Keep the sample goals panel beside the bands until #82. Nothing is removed before its epic. It lost because it breaks the two-column layout and puts sample goals next to real sprints.
- **D9 — Placing sprints under milestones (#93).** Each sprint goes under its placing milestone, comparing calendar dates, with a milestone's due date read in UTC. A milestone with no sprints still shows a header with no start date. A milestone with no due date takes no sprints, and its header sits after the last sprint band, before the no-sprint band. Each header's link opens the milestone's edit page in GitHub in a new tab, under the existing link rules. **Why:** GitHub stores a due date as a moment in time, and reading it in local time can move it a day and misplace a sprint. GitHub also allows a milestone with no due date. **Refuted alternative:** none
- **D10 — The current sprint's card carries the glow and a progress bar that counts all of its issues (#93).** The current sprint is the one whose start and end dates include today's local date. When several do, the earliest start wins. Its sprint card in the goal column is the only element that carries the glow, and that card shows the progress bar. No row and no part of the backlog column carries the glow or a bar. Progress is the closed share of every issue in the repository whose iteration on the sync source is that sprint, open and closed. It is read through the gateway, in a read that is complete or fails the load. **Why:** The backlog query returns open issues only, so a share counted over the band's rows would always read 0%. The glow and the bar describe the sprint, not its rows, so they belong on the sprint's card. **Refuted alternative:** Show the current sprint's closed issues as rows in its band, so one set of issues drives both the rows and the bar. It lost because it changes the backlog query, which the initiative leaves to the Settings page, and it fills the band with finished work.
- **D11 — Stacking under 760 pixels (#93).** Below 760 pixels, each band shows its sprint card above its rows, and the no-sprint band's card shows too. The goal column already comes first, so stacking needs no reordering. The divider hides, and milestone headers span the width. At 760 pixels and wider, the columns sit side by side with today's minimum widths. At 360 pixels, long titles and crumbs wrap or truncate, so nothing overflows sideways. **Why:** This is the mockup's stacking, and the minimum-width rule only means something where there are two columns. With the goal column first, the order on screen and the keyboard and reading order are the same at every width. **Refuted alternative:** none
- **D12 — The data rule changes in the standards, the stack page and the product context (#93).** The standards say Raiden owns its milestone, sprint, sprint goal and sprint assignment records, and GitHub is a sync source for milestones and sprints. A sync overwrites synced records and never Raiden-owned ones. The cache-only exception and the "never authoritative" prohibition are rewritten to match. The stack page's statement that the database holds only data GitHub cannot store changes too. The token rule says the backend may receive the lead's token on a request, never stores or logs it, and sends it only to GitHub's API. The ban on writing to GitHub and the "no issue editing" anti-goal stay, marked as lasting until the write-back epic. **Why:** The stack page repeats the rule story #87 removes, so leaving it would keep a written rule that contradicts the records. **Refuted alternative:** none
- **D13 — Story #85 documents how to deploy the backend's data path (#93).** Story #85 adds a deployment section to the setup instructions: the table, the backend's permission to read and write it, the cross-origin rule for the new data request, and the App's new permission. **Why:** The backend gains its first stored data in this epic, and a self-hosting team has no instructions for it. **Refuted alternative:** none
- **D14 — The App gains the organization-level Projects permission, read-only (#93).** The GitHub App's registration adds the organization-level Projects permission, set to read-only. No other permission changes, and no write permission is added. Projects owned by a person are not covered; their repositories get no synced sprints until #84. **Why:** The repository-level Projects permission the App has today does not reach an organization's projects, so without the new permission no organization repository would get synced sprints. A read-only permission keeps the rule against writing to GitHub. **Refuted alternative:** Keep the App's permissions unchanged and leave sprints to #84 for every repository. No team would need to update its App. It lost because organization repositories, the main case, would get no sprints from GitHub, which is this epic's purpose.
- **D15 — The goal column is on the left and the backlog column is on the right (#93).** At 760 pixels and wider, the band view puts the goal column on the left and the backlog column on the right. The column headings follow the same order. Below 760 pixels, the stacked page keeps this order: in each band, the card comes before the rows. The sample page is not affected and keeps its backlog on the left. **Why:** Grooming is for planning sprints toward their goals. The milestones, the sprints and their goals are the page's main surface, and the issues are the detail that fills each sprint. So the plan takes the first and most-read position, on the left. The order has a second benefit. The page shows the same order side by side and stacked, so keyboard focus and screen-reader order always match what the lead sees. **Refuted alternative:** The mock's order, with the backlog on the left and the goal column on the right. It matches the reviewed mock and the epic's original description. It keeps the sample page and the band view on the same sides, the arrow keys keep their current meaning, and the build already does it. It lost because it puts the plan, the page's main surface, in the second position, and because the stacked page would then show each card in a different place from its keyboard focus and screen-reader order.
- **D16 — The divider moves in the direction of the key, and the lead keeps one backlog width (#93).** The divider still reports the backlog width, and the lead keeps one preferred backlog width. That width applies to the backlog column wherever the column sits, on the sample page and in the band view. Left and Right move the divider in their own direction by a fixed step, and Shift gives a larger step. A pointer drag works the same way. In the band view, Left and a drag to the left widen the backlog. On the sample page, Left still narrows it. Home sets the backlog to its minimum width, and End sets it to its maximum. Double-click and Enter reset the default width. Fitting the shown width works as before, and the preferred width is never overwritten. **Why:** A divider is a visible bar, so a lead who presses Left expects it to move left. The accessible separator pattern specifies the same thing: the arrows move the separator, and the reported value is the size of the pane it controls. One preferred width keeps the lead's choice through the sample page's removal in #82, with no change to stored data. **Refuted alternative:** Keep the page's current rule that Left narrows the backlog and Right widens it. The grooming-backlog-view page's wording and the existing tests stay as they are. It lost because in the band view Left would move the divider to the right, which contradicts what the lead sees and the separator pattern that #8 chose the divider for.
- **D17 — A sprint's name, dates, glow and progress sit on its card in the goal column (#93).** Each band has one sprint card in the goal column. The card shows the sprint's name and dates and leaves empty room for the goal. The no-sprint band's card says that its issues have no sprint. The current sprint's card adds the glow and the progress bar (D10). Milestone headers sit in the goal column. The backlog column holds only issue rows and their crumbs, with no sprint label, dates, glow or bar, and it is empty beside a milestone header. A card shows no goal field, no sample goal, no met or missed pill and no prompt to drag issues, because those belong to #82 and #83. **Why:** This matches the mock and the amended #81, #88, #90 and #91. The backlog column becomes a plain list, which is what the one search of #82 and the drop targets of #83 need. Room on the card means #82 adds the goal where the name already is, so it does not move the label. The mock's prompt to drag an issue into a sprint would be false, because live rows cannot be dragged. **Refuted alternative:** The current build. The sprint's name, dates, glow and bar sit at the top of its rows in the backlog column, and the goal column stays empty until #82. It is built and tested, and it needs no card yet. It lost because the goal column would hold nothing in this epic, #82 would have to move the label anyway, and the label would break the row list that #83 drops onto.
- **D18 — The band view's default backlog width is 58% of the view (#93).** In the band view, when the lead has set no preferred width, and after a reset by double-click or Enter, the backlog column takes 58% of the view's width, fitted to both minimum widths. The sample page keeps its current default. A preferred width the lead sets still applies on both pages, as D16 describes. **Why:** The lead chose to give the issue list most of the width. Until #82 fills the cards, the goal column holds only names and dates, and issue titles need the room. 58% is the mock's split. **Refuted alternative:** Keep today's fixed default for both pages until #82. It changes nothing recorded and is the simplest change to undo. It lost because the goal column would take about two thirds of a wide page while it holds only names and dates, and long issue titles would wrap.
- **A failed backend request keeps its failure kind and adds an optional reason from a fixed list (project-unreadable).** (a decision stub the verdict on sameera/raiden#94 confirmed). **Why:** The page must name an unreadable project apart from an unreadable repository, and a fixed list keeps free backend text out of pages. **Refuted alternative:** A new failure kind per backend cause.
- **Partition repo#<databaseId>; sort keys source, sprint#<fieldId>#<iterationId>, milestone#<milestoneId>; a sync touches only origin=github records under its own prefixes.** (a decision stub the verdict on sameera/raiden#94 confirmed). **Why:** Later goal and assignment records can live in the same partition without a sync matching them. **Refuted alternative:** One attribute map per repository, rewritten whole by a sync.
- **Below 760px the expanded sidebar overlays the page, with a 56px rail margin on the main area.** (a decision stub the verdict on sameera/raiden#94 confirmed). **Why:** The page fits a 360px window in both sidebar states and the stored collapse choice stays true. **Refuted alternative:** Force the sidebar collapsed below 760px.
- **Live rows lose drag and the grip but keep Alt+Up and Alt+Down moves.** (a decision stub the verdict on sameera/raiden#94 confirmed). **Why:** Live-backlog invariant 7 forbids dragging a live row, not keyboard moves. **Refuted alternative:** Remove all reordering of live rows.
- **Every band-view row is a CSS grid with the same three tracks; a band is a card then its rows in DOM order at every width.** (a decision stub the verdict on sameera/raiden#94 confirmed). **Why:** D15 and G43 need the card before its rows in focus order at every width, and the columns must line up. **Refuted alternative:** Flex rows with order swaps when stacked.
- **The sprint card has a minimum height and no placeholder element for the goal.** (a decision stub the verdict on sameera/raiden#94 confirmed). **Why:** G46 forbids a goal field on the card, and an empty box would read as one. **Refuted alternative:** An empty bordered goal area.
- **The band divider is absolutely positioned against .rd-bands at full height and paints only on hover or focus.** (a decision stub the verdict on sameera/raiden#94 confirmed). **Why:** With panel borders gone, the divider needed to show where to grab without drawing a column edge. **Refuted alternative:** A divider cell in every band row.
- **Add !.env.frontend.local to .nxignore so the build input is hashed.** (a decision stub the verdict on sameera/raiden#94 confirmed). **Why:** Nx drops gitignored paths from its file map, so a cached build baked in stale team settings. **Refuted alternative:** A runtime cat input in each build target.
- **A separator labelled 'No milestone' before the first sprint with no placing milestone, shown only when a milestone header comes before it.** (a decision stub the verdict on sameera/raiden#94 confirmed). **Why:** A loose sprint right after the last milestone read as sitting under it; a labelled rule says it does not and is not a milestone header. **Refuted alternative:** A plain unlabelled gap.
