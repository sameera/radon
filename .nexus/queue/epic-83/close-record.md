# Close Record: The lead moves issues between sprints in Grooming

## Key Decisions

- **D1 — One sprint assignment record per issue, holding a sprint or an explicit no-sprint mark (#118).** Each issue has at most one sprint assignment record for the repository, keyed by GitHub's permanent identity for the issue and shared by everyone who opens that repository's Grooming. The record holds a sprint's identity or the no-sprint mark. A move overwrites it. This epic never deletes it. An issue with no record follows GitHub. **Why:** The epic assumes one sprint per issue for the repository, shared by everyone. The issue's identity survives a transfer, which the issue number does not, and #93 already reserved this record shape beside sprints, milestones and goals. The explicit mark is needed for #114 AC2: an issue dropped on the no-sprint band while GitHub holds a sprint must stay there after a reload, which "no record" cannot express. **Refuted alternative:** Key the record by issue number. It is readable, and the backend could check it without an identity lookup. It lost because a transferred issue changes its number, and the record would then attach to the wrong issue.
- **D2 — A move has its own backend route, with the role, issue and sprint checked on every write (#118).** A move write goes to its own backend route, beside the goal write, with the same origin and token checks. On every write the backend makes one GitHub query as the caller, which gives the repository's identity, the caller's role and the repository the issue belongs to. It refuses a caller below maintain, an issue outside the repository, and a target that is neither the no-sprint mark nor a sprint record of the repository. It then writes only that issue's record. It never runs a sync and never writes to GitHub. The page sends only the issue's identity and the target. **Why:** This mirrors #82's goal write, which the lead approved, and the role read it uses is proven in production. The backend is reachable from the internet, and its origin check stops browsers, not scripts, so the role must be checked on the write. The issue and sprint checks keep the shared store free of records for foreign issues and missing sprints, at no extra request. A separate route means a move can never start a sync. **Refuted alternative:** Trust the page's may-edit flag and the issue identity it sends, and skip the GitHub read on each move. Every move would be one round trip cheaper. It lost because any script holding a valid token for a repository it can read could then rewrite the team's plan.
- **D3 — Assignments arrive with the Grooming sync's answer (#118).** The page reads sprint assignment records only from the Grooming sync's answer, which already returns every record for the repository. There is no separate read and no live refresh. **Why:** #93 returns all of the repository's records with one store query, and bands show only after a complete load. A separate read would add a request and a failure path and give nothing. This is the pattern #82 used for goals. **Refuted alternative:** none
- **D4 — The page merges Raiden's sprint with GitHub's sprint and computes the flag (#118).** The shown band is the Raiden sprint's band when the issue has a Raiden sprint, and otherwise the GitHub sprint's band. The flag shows exactly when the issue has a Raiden sprint that differs from its GitHub sprint, with no sprint counted as a value on both sides. The flag names the GitHub sprint, or says GitHub has none. It is worded text with an attention tint, never color alone, and it is not a control. Every viewer sees it. The no-sprint band's card text changes from "Issues with no sprint in GitHub" to say only that its issues have no sprint. **Why:** This is the initiative's settled rule, made exact enough to check against the epic's success metric that only rows whose sprints differ carry the flag. The page already works out the GitHub sprint during the backlog load, and doing it in the backend would send issue data there. The design system requires worded status. **Refuted alternative:** The backend merges and returns each issue's shown band, keeping one copy of the rule. It lost because the backend would have to read every issue's iteration from GitHub on each load, repeating the browser's backlog read, which #93 already refuted.
- **D5 — A move always stores the lead's choice, even when it equals GitHub's sprint (#118).** A move to any band other than the row's current band writes the target, including when the target equals the issue's GitHub sprint. The flag then disappears because the two sides match, and the record stays. A drop on the row's current band sends nothing. No equality check ever deletes a record. This epic adds no action that hands an issue back to GitHub's sprint; the write-back epic decides that. **Why:** #115 AC2 requires a moved issue to stay in Raiden's sprint when GitHub later changes, and a move back to the GitHub sprint is a choice the lead made too. Deleting on equality would hand the issue back to GitHub without notice. Storing is the reversible choice: a later epic can prune records that equal GitHub, but a deleted choice cannot be recovered. The lead confirmed this at the clarification gate. **Refuted alternative:** Delete the record when the target equals the GitHub sprint, so Raiden holds only real disagreements and the issue follows GitHub again. It lost because it breaks "Raiden's sprint wins" for that issue, and the lead cannot see the change.
- **D6 — Show the move at once, write one move at a time per row, and roll back to the saved band (#118).** A move shows at once. Each row has at most one move write in flight, and a newer move made during a write is sent after it, as the newest target only. On a failure the page drops any waiting target, puts the row back in its last saved band, and says in an announced status message that the move of that issue was not saved, with a short cause. Focus stays on the row wherever it shows. A write stays tied to the repository and issue it was made for. There is no automatic retry and no undo. **Why:** #114 AC5 needs a rollback, and #116's repeated key presses need an ordering that never lets an older target land last. This is the pattern #82 used for goals. "The band it came from" means the last band Raiden confirmed, because otherwise a rollback during quick moves would land in a band that was never saved. **Refuted alternative:** Wait for the backend before moving the row, with a busy state. It is simpler and never shows an unsaved state. It lost because every key press would wait a round trip of about half a second or more, which makes stepping across several bands slow.
- **D7 — An assignment to a sprint Raiden no longer holds is ignored, not deleted (#118).** When a record names a sprint that the store no longer holds for the repository, because the iteration was deleted in GitHub or the sync source was picked again, the page treats the issue as having no Raiden sprint. The row shows in its GitHub band with no flag. The record stays until the next move overwrites it. Ended sprints are not affected, because GitHub keeps completed iterations. **Why:** The sync must never touch records keyed to an issue, so the page has to decide what an orphan means. Placing the row in the no-sprint band would claim the lead chose no sprint, which is false. Following GitHub is the only placement that states nothing untrue. **Refuted alternative:** Show orphaned rows in the no-sprint band with the flag, so the lead notices the lost plan. It lost because it puts a "no sprint" claim on issues the lead never put there, and the flag would point at a disagreement the lead did not create.
- **D8 — Rows are draggable again for editors, the band is the drop target, and the row lands at the top (#118).** For editors, each issue row can be dragged with the browser's own drag and drop. The drag carries only the drag marker, and a drop with anything else does nothing. A drag that starts on the issue's link moves the row and carries no link. Every sprint band, past, current and future, and the no-sprint band accept a drop on their card or rows. Milestone headers and the "No milestone" break do not. The dropped row goes to the top of the target band. Only the dragged issue moves; its children keep their own sprints and stay in their bands under the moved parent's crumb. Non-editors get no draggable rows. **Why:** #114 needs drag between bands. The marker rule and the link rule are grooming-plan-moves invariants 1 and 5, proven on the sample plan, and they matter more in the extension, where GitHub's page sits beside Raiden. Order inside a band is lost on reload, so exact drop placement has little lasting value, and Alt+Up and Alt+Down fix the order afterwards. Past sprints accept drops for the same reason #82 kept past goals editable. **Refuted alternative:** Insert the row where it is dropped among the target band's rows, for more exact placement. It lost because it needs row-level drop zones and before or after rules in every band, for an order that resets on reload, and it would differ from the keyboard rule.
- **D9 — Alt+Shift moves to the neighbouring band in band order, and Alt alone still reorders (#118).** On a focused row, Alt+Shift+Down moves the row to the top of the next band in band order, and Alt+Shift+Up moves it to the bottom of the previous band, skipping milestone headers and the "No milestone" break. The no-sprint band is always last. From the last band Alt+Shift+Down does nothing and sends nothing, and the same holds for Alt+Shift+Up from the first band. A band with no shown rows is still a band. Alt+Up and Alt+Down without Shift keep today's reorder inside the band, send no request and work for everyone. The move saves as in D6, and focus follows the row. A non-editor's Alt+Shift press moves nothing. **Why:** These are #116's criteria. Top of the band below and bottom of the band above keep the row next to where it was, so repeated presses walk through the bands in order. Following on-screen order keeps the keyboard and the eye in agreement in both side-by-side and stacked layouts. **Refuted alternative:** none
- **D10 — The design-system rule on edit controls extends to sprint moves (#118).** The design system's rule "Read-only on GitHub data" is amended so that Raiden data includes sprint goals and sprint assignments. A row's drag and its keyboard move are edit controls on the issue's sprint in Raiden. The issue's title, number, iteration and fields still look read-only. The flag is a status, not a control. **Why:** The rule today names only sprint goals as editable. A draggable issue row would break its letter while keeping its intent, which is that Raiden never makes GitHub data look editable. A written change is better than a silent deviation. **Refuted alternative:** none
- **D11 — "Holds no sprint" means "has no sprint assignment" (#118).** #115 AC4 means an issue with no usable sprint assignment record: never moved, or orphaned as D7 describes. It does not mean an issue that Raiden records as having no sprint. **Why:** As worded, #115 AC4 contradicts #114 AC2. An issue dropped on the no-sprint band "has no sprint in Raiden", and AC4 would then send it back to its GitHub band. **Refuted alternative:** none
- **D12 — The current sprint's progress bar keeps counting GitHub's sprint (#118).** The current sprint's progress bar keeps counting the sprint's issues in GitHub, as #93 decided. It does not count by Raiden's sprint in this epic. The write-back epic revisits it. **Why:** Counting by Raiden's sprint would need a further GitHub read of state and iteration for every closed issue that holds a move, and no story of this epic asks for it. The lead confirmed this at the clarification gate. **Refuted alternative:** Count the bar by Raiden's sprint, so it matches the band's rows. It lost on the extra GitHub read and on scope that none of #114, #115 or #116 covers.
- **Move write is POST /grooming/move with one combined GitHub check (MoveCheck)** (a decision stub the verdict on sameera/raiden#119 confirmed). **Why:** D2 asks for one GitHub query per write; one request keeps it at one round trip **Refuted alternative:** reuse the goal write's repository query plus a second node query
- **Assignment record is assign#<issue node id> holding sprint or none; null on the wire for the no-sprint mark** (a decision stub the verdict on sameera/raiden#119 confirmed). **Why:** the no-sprint mark must differ from no record, and null cannot collide with a sprint id **Refuted alternative:** a reserved string such as "none" as the sprint value
- **The shown-band merge lands with #114, the flag with #115** (a decision stub the verdict on sameera/raiden#119 confirmed). **Why:** #114 AC1 and AC2 need Raiden's sprint to win on reload **Refuted alternative:** keep all of the merge in #115
- **Backend reason unknown-sprint passes through the gateway** (a decision stub the verdict on sameera/raiden#119 confirmed). **Why:** D6 names the sprint no longer exists as its own failure cause **Refuted alternative:** map every 409 to that cause
- **The flag is an attention Pill reading "In GitHub: <sprint>"** (a decision stub the verdict on sameera/raiden#119 confirmed). **Why:** the Pill is the design system's worded status with an attention tint **Refuted alternative:** an icon with a tooltip
- **Focus after a band move is restored by the page, not the band** (a decision stub the verdict on sameera/raiden#119 confirmed). **Why:** a move between bands re-creates the row in another band's list **Refuted alternative:** move the row's DOM node between bands by hand
